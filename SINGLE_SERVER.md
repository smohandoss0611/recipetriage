# Streamlit, FastAPI and PostgreSQL on one server

This deployment uses one Linux machine and four Docker containers. It does not use `share.streamlit.io`, a separate public backend hostname or the paid Render proposal. The existing React development stack remains in `docker-compose.yml`; this is a standalone `compose.server.yml` deployment.

```text
Browser → HTTPS :443 → Caddy → Streamlit :8501
                                ↓ private Docker network + API token
                             FastAPI :8000
                                ↓ isolated database network
                             PostgreSQL :5432
```

Only Caddy publishes ports. FastAPI, Streamlit and PostgreSQL have no host port mappings. Streamlit uses the fixed internal address `http://backend:8000`; the explicit Docker mode accepts only that origin with a token of at least 32 characters. Public browser traffic uses HTTPS. Private container traffic stays on this single host. RecipeTriage opens directly without an app sign-in screen. Anyone who can reach the interface can use its shared recipes and administrative features. Local-check mode binds only to this computer; a public deployment needs access restrictions at the host or gateway when the workspace should remain private.

## If Compose says it cannot find `.server/compose.env`

The source package does not include deployment credentials. `.server/compose.env` and the other three env files are generated by the first-install setup command below. Even `down` needs those files to parse `compose.server.yml`. The temporary verification setup was removed after testing; it is not your configured server deployment.

If your goal is to stop the **existing local React/FastAPI/PostgreSQL/MLflow Docker stack**, run this from the project root:

```sh
docker compose -f docker-compose.yml --profile tracking down
```

That command keeps named data volumes. A standalone Streamlit process on port 8501 is separate; stop it with Ctrl+C in its own terminal.

If your goal is to install the **new single-server stack**, complete `python3 infra/server/setup.py` on that server first, then use its Compose commands. For an intentional local TLS test, use the `--local-check` option described at the end of this guide. Do not create an empty env file to suppress the error. If configuration is lost from a previously initialized deployment, restore its original private files instead of generating different database credentials.

## First installation on your Linux server

Use Docker Engine with Compose **2.30 or newer** and Python **3.11 or newer** for the setup/backup tools; container Python is 3.12. Docker's [installation instructions](https://docs.docker.com/engine/install/) vary by Linux distribution. Start with approximately 4 CPU cores, 8 GB RAM and 50 GB disk for this small CPU learning model, then measure actual workload use. This is a sizing estimate, not a purchased plan or a capacity guarantee; larger training runs need separate sizing.

1. Copy/extract the reviewed source onto your server and open a terminal in its repository root. Upload source without `.env`, `.server`, `.streamlit/secrets.toml`, environments or caches. You can use the source ZIP; GitHub is optional for this deployment.
2. Point your chosen domain's DNS A record to the server's public IPv4 address. Configure an AAAA record only if IPv6 actually routes to the same server. Allow inbound TCP 80/443 and restrict SSH to your access needs. Do not expose 5432, 8000 or 8501.
3. Run these commands from the repository root:

   ```sh
   python3 infra/server/setup.py
   docker compose --env-file .server/compose.env -f compose.server.yml config --quiet
   docker compose --env-file .server/compose.env -f compose.server.yml up --build -d --wait --wait-timeout 240
   docker compose --env-file .server/compose.env -f compose.server.yml ps
   ```

   Setup prompts for the real hostname (no `https://`) and optional Fireworks key. Key entry is hidden. It generates independent API/database secrets; no workspace password is needed. It refuses to overwrite an existing `.server` directory. First image builds can take several minutes; model weights download when first used.

4. Open `https://` followed by the hostname you entered. The app opens directly. Select **Check backend connection**, then use the workspace tabs and page tabs to inspect Recipes and the learning labs. No public deployment is claimed until this succeeds on your real domain.

Caddy obtains and renews certificates and redirects HTTP to HTTPS when DNS and ports are configured correctly. Its reverse proxy supports Streamlit WebSockets. [Caddy HTTPS requirements](https://caddyserver.com/docs/automatic-https), [reverse proxy documentation](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy).

If startup fails, retain the actual error:

```sh
docker compose --env-file .server/compose.env -f compose.server.yml logs --tail=100 gateway streamlit backend postgres
```

An HTTPS error usually needs a DNS/port check; a healthy Streamlit process alone does not prove that the database or models are ready. Keep raw secret files and full `docker compose config` output private. `config --quiet` validates without printing resolved credentials.

## Files and credentials

| File | Purpose |
| --- | --- |
| `compose.server.yml` | Four services, isolated networks, startup checks, persistent volumes |
| `infra/server/Caddyfile` | Domain, automatic HTTPS and Streamlit reverse proxy |
| `infra/server/Dockerfile.streamlit` | Small non-root Python UI image; no PyTorch or credentials |
| `infra/server/setup.py` | Private first-install configuration generator |
| `streamlit_ui/settings.py` | Choose Docker environment settings or the existing Community Cloud secrets |
| `infra/server/backup.py` | Maintenance backup with database/artifact checksums and automatic service recovery |
| `.server/compose.env` | Domain and public port settings |
| `.server/backend.env` | API token, database credentials and optional Fireworks settings |
| `.server/postgres.env` | Database initialization credentials |
| `.server/streamlit.env` | API token and optional MLflow link; no database password or Fireworks key |

`.server` is ignored by Git, Docker builds and delivery packaging. Setup creates its directory with mode 0700 and credential files with mode 0600 on Linux/macOS. Compose reads these files on the host and injects per-service environment values at runtime. They are not an encrypted secret vault; the server administrator and Docker administrator can inspect them. `env_file: format: raw` preserves literal secret characters without Compose interpolation. [Docker env-file reference](https://docs.docker.com/reference/compose-file/services/#env_file).

The current `.env` is not copied or consumed by this separate stack. To enable hosted inference later, edit `FIREWORKS_API_KEY` in `.server/backend.env` privately and recreate the backend with `up -d backend`. Managed SFT needs its separate account/model/deployment-shape settings. Missing access produces an explicit provider error. No model calls or training happen merely by starting the stack.

To rotate the API token, update both backend and Streamlit env files to the same new random token, then recreate both services. Existing `WORKSPACE_PASSWORD_HASH` values are ignored; the upgrade does not require editing or regenerating your private `.server` files. Changing `POSTGRES_PASSWORD` in env files does **not** change an initialized database password; rotate it inside PostgreSQL and update both credential files together.

## Data, backups and restart

The Compose project is `recipetriage-server`; its named volumes are distinct from the existing local React stack. A new server starts with seven unreviewed seed recipes. Existing reviews, preference choices, recipe edits, runs, registry rows and large exported models are **not automatically migrated**. See [the migration guidance](STREAMLIT_DEPLOYMENT.md#data-and-model-lineage-during-migration) to preserve your database and matching artifacts before first backend startup.

PostgreSQL persists in `postgres_data`. Model cache, training runs and deployment exports persist in `model_data` under `/data`. Caddy certificates persist in `certificates`. Ordinary `down` or container recreation retains these volumes. **Do not use `down --volumes` on a deployment containing data you need.**

Before backup, wait for running experiments to finish. The following command briefly stops Streamlit and FastAPI to capture matching database and artifact state, then restarts them even if the backup fails:

```sh
python3 infra/server/backup.py --maintenance
```

It saves `database.dump`, `artifacts.tar.gz` and `manifest.json` under `.server/backups/<UTC timestamp>/`. The archive contains training and deployment artifacts, not the downloadable Hugging Face cache. A missing manifest means the backup did not finish. The script streams binary output through Python, so it avoids PowerShell binary-redirection problems. Copy complete backups to private storage away from this machine; a backup kept only on the server does not protect against losing the server. Keep an encrypted copy of configuration separately.

Restore into a **new empty database and model-data volume before starting the backend**. Verify both file hashes against the manifest, restore the custom database dump using PostgreSQL 17 `pg_restore --exit-on-error --no-owner --no-acl`, and extract the matching artifact archive into `/data` preserving ownership. Never restore over a running or already initialized application. The setup package does not automatically delete/overwrite existing destinations. The backend's UID 1000 must own restored training/deployment directories.

To stop or start the application while preserving data:

```sh
docker compose --env-file .server/compose.env -f compose.server.yml down
docker compose --env-file .server/compose.env -f compose.server.yml up -d --wait --wait-timeout 240
```

Training uses one backend process and an in-process job runner. Stopping/deploying during training interrupts that run; recovery records interruption rather than automatically resuming. Keep one backend instance and avoid deployments during active jobs. Human-review requirements, explicit preference choices and model promotion gates still apply. This hosting work does not improve benchmark scores or promote any candidate.

## Local verification and platform alternatives

The deployment target is Linux. Docker Desktop can run the same Linux containers on macOS/Windows for testing. On Windows replace host `python3` with `py -3.12` (or another installed Python 3.11+); Docker commands are unchanged. Protect the `.server` directory with appropriate Windows ACLs because POSIX modes do not provide the same protection there.

`python3 infra/server/setup.py --local-check` selects loopback-only ports 8580/8543 and hostname `localhost`. This is an isolated TLS test, not a public deployment. Caddy uses its own local CA for localhost; browsers will not trust it automatically. Do not disable certificate verification globally. A test client can use the exported CA certificate explicitly; no OS trust-store modification is required. Do not reuse a local-check configuration as your public deployment.

The existing local React app remains at 8080; the earlier standalone Streamlit preview remains at 8501 when running. MLflow is not exposed by this stack; the app still keeps its experiment registry in PostgreSQL and can store local MLflow artifacts on the persistent backend volume. An optional remote MLflow dashboard needs its own authenticated host configuration.
